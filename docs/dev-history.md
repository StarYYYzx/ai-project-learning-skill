## 阶段一 · 方法论设计

起点是一个设想：找一个成熟、常用于技术学习的项目，由教学 AI 拆解出模块与核心算法；然后把项目重排成一串逐步交付的需求，让学生先自己写 MVP（技术栈、算法全部自主选择），再由教学 AI 把学生作品与项目对照、记录优缺点；一轮轮推进，直到完整重建整个系统。

这个初始设想在落地前经过四轮关键取舍，最终结论沉淀在阶段二的 `00_方法论设计.md` 里：

1. **对照策略**：自主选型会让技术栈与基准不一致，而"对照原项目"需要可比性。曾权衡的选项之一是"指定技术栈换取可比性"，最终选择折中方案——架构层自由对照（比设计决策），关键算法用固定场景定点比拼（比实现细节）。
2. **迭代驱动方式**：初始设想是"告诉学生系统有哪些缺陷"。改为增量需求驱动，理由是缺陷驱动暗含"AI 心里有标准答案"，会把自主产出退化成猜答案。这一修正被明确记录在 `00_方法论设计.md` 的"设计修正记录"中。
3. **角色架构**：定为双 AI——指导老师持有教案，协作助手不知道答案。信息隔离是前提，否则对照退化为抄作业。
4. **完成标准**：定义为达成教学目标，而不是复现基准的全部功能。

同批修正还包括：对照后增加反思环节、增加理解验证与"对 AI 输出保持批判"的要求。

**遗留**：这轮设计的讨论过程没有归档，只有结论。当时权衡过哪些具体备选方案、被否的理由是什么，缺乏一手记录。

## 阶段三 · 通用化：v0.1.0（2026-09-08，提交 `5298a7d`）

RAG 资料包完成后，紧接着的目标是把这套方法从"某个项目的专用流程"变成"指定任意项目都能跑"的通用 skill，并开源到 GitHub。

关键决策：

1. **命名与仓库**：skill 名 `ai-project-learning`，仓库 `ai-project-learning-skill`。
2. **运作模式定两种**：单 AI 全流程（默认，一个 AI 分阶段切换指导与协作角色）与双 AI 严格信息隔离（用 `roles/` 下两个独立 skill 分别装入两个窗口）。
3. **目录结构**：主 `SKILL.md` 保持精简，方法论下沉到 `references/` 按需读取；角色 skill 独立放在 `roles/`，可单独安装。
4. **泛化方式**：把 RAG 专用角色 skill 里的项目特定内容剥离，角色职责、守则与红线保留为通用条款。

## 阶段四 · 交流规范：v0.2.0（2026-09-08，提交 `e751af0`）

作者在试用中暴露两个问题：一是教学 AI 在决策提问里使用专业名词，初学者被术语挡住无法决策；二是 AI 会给出倾向性推荐，学生容易"跟着推荐走"，自主决策形同虚设。

由此确立四条规则，写入新增的 `references/communication-guide.md`：

1. **术语脚手架**：关键概念首次出现时附一行"它在本项目里管什么"，不展开长文；并明确判断标准——解释通用概念不算泄露答案。
2. **提问邀请**：每轮开场明示可随时打断提问，兜住初学者"不知道自己不知道"的情况。
3. **禁止倾向性推荐**：列出禁用词，规定被反问"你推荐哪个"时不给倾向答案，改用提问反推学生的约束条件。
4. **项目学习笔记**：这条的定位经过一次调整——最初设想是"学习笔记由学生自己写，兼顾元认知"，后改为由 AI 代写。理由是学习已经发生在"询问 → 思考 → 决策"的过程中，笔记只需承担留档回看职责，而"是否真的学会"由理解验证环节负责。这一分工在 v0.2–v0.5 沿用，v0.6 扩展为八类项目档案。

同时修复了一处规则冲突：协作助手 skill 中写着"可以推荐，但不替他拍板"，与禁止倾向性推荐的规则直接矛盾，改为禁止推荐。

**同期产物**：一篇面向微信公众号的推广文章（属对外材料，未纳入仓库）。

**遗留**：本阶段没有独立的升级记录文档，其起因与决策只在本文件与 `CHANGELOG.md` 中留存。

## 阶段六 · 决策中立化：v0.4.0（2026-09-14）

起因是一个复发问题：v0.2 已经立下"禁止倾向性推荐"的规则，但实践中 AI 在提供可用方案时仍带有推荐。根因不在用词，而在规则结构——旧规则禁止"推荐"字样，同时允许"给出选项与各自权衡"，而权衡本身就构成评价："X 更轻量""X 适合快速验证"这类描述即使不含"推荐"二字，框架已经倾斜，选择随之被引导。

本轮把"评价出现的时机"引入规则：

- **决策前**：只做对称的中性枚举。每个选项给"它是什么"的事实属性——依赖、运行环境要求、涉及组件、许可，所有选项用同一组维度、长度相当；评价性形容词与适用性判断一律不出现。
- **决策后**：先请学习者讲自己的理由与预期代价，再由 AI 说明他选的这条路的利弊、相对其他选项放弃了什么。措辞针对所选方案，不用"我本来推荐…"评判选择。
- **被追问时**：把约束条件反推给学习者；即使他说"你替我定"，也只补中性事实，不替他选。

这次升级同步做了一次一致性审计：旧规则的影响面不止一处，示例文档、README、评估用例中都有与之冲突的表述（示例里的选项描述带评价、只给单侧缺点），一并修正，避免"课本与老师打架"。

决策后"先请学习者讲理由"这一步是在实现中补上的——如果 AI 先说利弊，学习者就只剩复述，理解验证会失去意义。这个顺序保证利弊分析仍然是学习者思考的补充，而不是替代。

**残留风险**：中性枚举的信息量低于带评价的权衡，初学者可能更难决策。规则允许给事实属性来缓解，但效果需要在实际使用中观察。

**另有一处非代码事件**：作者在 GitHub 网页上直接为 README 添加了一段手写开篇（自嘲"这段是人写的，后面全是 ai 写的"并说明做这个 skill 的动机），对应远程提交 `69275e8`（2026-09-08 20:09）。本地推送时该提交与新版 README 合并，合并提交为 `816f543`（2026-09-14）。



## 阶段七 · 提问方式改造：v0.5.0（2026-10-20）

起因来自实际使用：AI 客户端自带的"提问 / 选项"类工具（结构化选择题、单选卡片、弹窗确认，统称 Ask 工具）会把回答压缩成几个可点的按钮。学生面对不熟的选项，会"没读懂也随手点一个"，跳过"理解 → 权衡 → 表达"这个过程——而这恰是学习发生的地方。按钮式回答只有一两个词，看不出学生是否真想清楚，后续也无法据此给脚手架。

本轮把"输入的征求方式"引入规则，改造是补一条而非改一条：

- **默认不用 Ask 工具**：问题、选项与事实属性一律写在对话正文里，留白，等学生用自己的话回复。
- **不把短回复当决策**：学生只回一个词或含糊其辞时，先追问理由，不替他补全，也不当成已决策往下推进。
- **窄例外**：纯机械、无学习意义的确认（是否继续下一轮、是否归档记录、是否导出角色配置）可给简洁选项，但同样写在对话里。

同步落点与前几轮一致：`communication-guide.md` 新增第 5 节、主 `SKILL.md` 纪律表新增"征求学习者输入"一行并在阶段 0 明确要求、两个角色 skill 各自补一条红线、`evals` 新增用例 5（避免"课本与老师打架"，沿用 v0.4 的一致性审计做法）。

**残留风险**：规则只约束 AI 的行为，无法阻止学生主动要求"给我几个按钮选"。若学生在不熟的领域直接索要选项，AI 仍应把选项写在对话里，并顺带给出事实属性。

## 阶段八 · 粒度与对照重构：v0.6.0（2026-10-29）

起因是一次目标人群复盘：本 skill 原本预设"会写代码、但没做过完整项目"的学习者，而作者的实际设想更宽——面向没有大型项目经验、习惯"许愿式编程"的人。这轮把设想重新表述为：从一个小需求开始，先做设计与 MVP，再按敏捷方式逐个小步骤推进；每个小步骤的设计与关键算法由学习者充分决策，AI 只承担代码实现；决策完成后与原项目比较并做教学讲解；每次有意义的交流都落成文档，文档同时记录学习进度与开发进展；遇到陌生概念随时提问并记入文档。

作者同时明确否定了一条旧规则：**不能一概而论压缩成 4-8 个增量**。大型项目 8 个远远不够，简单项目 4 个也太少。旧规则把"小项目经验"当成了通用约束。

本轮的六项改动：

1. **三层粒度**：项目 → 里程碑（可演示的价值单元）→ 小步骤（单一可验证交付、1-2 个决策点）。数量由规模推导，不再设固定轮数；大型项目用"学习范围切片 + 滚动规划"处理。
2. **先软件工程分析，再细拆**：阶段 1 先跑通基准（安装、测试、示例），再做模块地图、依赖与数据流、质量属性、架构决策与可教学点；任务级只拆当前与近期，其余里程碑保持粗粒度。
3. **实现主体改为 AI**：用户负责设计与决策，AI 按定稿设计写代码。理解验证随之调整——不再要求用户手敲，而是要求讲清设计，并指出 AI 实现中一处可疑、想改或没看懂的地方。
4. **分级揭示**：决策前完全隔离；决策后·实现前只讲所选方案的利弊；小步骤末才与原项目对比；里程碑末汇总完整对照表。
5. **接受二元决策的泄露**：两个选项时，"你的选择与原项目不同"必然暴露原项目选了另一个。作者确认接受这部分泄露，换取小步骤末的即时教学；多选项决策仍只描述维度差异。
6. **项目档案**：从"节点式学习笔记"升级为八类文件——总进度表、软件工程分析、里程碑路线、单步实现档案、单步对照档案、里程碑汇总、术语表、评测记录；实现侧与对照侧文件在双 AI 模式下物理分开。

这轮被权衡过的选项：

| 决策点 | 曾权衡 | 最终选择 | 理由 |
|---|---|---|---|
| 轮数 | 固定 4-8 / 按规模推导 | 按规模推导 | 固定数字会挤压大型项目的教学点，也会让小项目显得空洞 |
| 拆解深度 | 全量前置 / 滚动 | 里程碑全量 + 步骤滚动 | 大型项目全量拆到任务级成本高且易过时 |
| 对照时机 | 完全隔离到结束 / 每个决策后立即 / 分级 | 分级揭示 | 兼顾即时教学与后续决策的自主性 |
| 二元决策 | 延后 / 只披露约束 / 接受泄露 | 接受泄露 | 即时教学优先；泄露发生在决策完成之后 |
| 实现主体 | 用户手写 / AI 实现 | AI 实现 | AI coding 时代，学习价值在设计与判断，不在打字 |
| 文档粒度 | 每次交流一份 / 每步一份 + 总表 | 每步一份 + 总表 | 兼顾完整性与可检索性 |

**残留风险**：

- 二元决策的泄露会锚定后续决策。规则只能禁止"把已揭示的做法当推荐"，无法消除学生心里的锚。
- AI 写代码容易让学习者"设计完就不读代码"。理解验证要求指出一处可疑之处，但执行强度依赖 AI 是否追问到位。
- 大型项目即使切片，学习周期仍可能很长；切片范围需要用户自己判断。
- 档案从一类变八类，维护成本上升；目前由 AI 承担写作，用户只做回看，实际负担待观察。
- 新增的行为用例尚未实跑。

## 阶段九 · 能力与工程保障：v0.7.0（2026-10-29）

起因是作者对长流程的三个疑问：学习结束后怎么保证做出来的系统与目标应用能力相当；流程拉长后怎么保证 skill 不丢上下文；学习者的设计是否只能是选择题，出现大偏移或原系统没有的新决策点怎么办。作者认可"能力基线 + 会话恢复 + 决策三分 + 偏离评审"的方案，并补充要求：新项目开始时先引导 Git 建库，每个阶段实时规划提交，目标偏移用建分支处理。

本轮五项改动：

1. **能力基线**：每里程碑从基准抽 5-10 条黑盒用例，只看输入与可观察输出，与实现无关；里程碑验收必须全过。收尾用 `notes/parity.md` 给出能力矩阵。"差不多"被明确为能力等价，不是代码相似。
2. **会话恢复**：新会话或"继续"时先读进度表、路线、当前档案并检查 Git 状态，再用三行复述。只加载当前步骤、上一步对照与里程碑汇总，避免把全部历史塞进上下文。
3. **决策三分**：封闭决策给选项；半开放决策给约束与维度、由用户先提方案；开放决策标记"无基准答案"。不再把所有决策压成 2-3 个选项的选择题。
4. **偏离控制**：以能力基线失守、后续里程碑不可达、评测回归、范围爆炸为判据，分局部 / 结构 / 目标三级；偏离评审只给事实与代价，由用户选择调整、裁剪或分叉。目标偏移建 `goal/<slug>` 分支，主分支保留原路径。
5. **Git 工作流**：阶段 1 `git init -b main`、`.gitignore`、教案首次提交；每个小步骤一次提交；每个里程碑打标签；目标偏移建分支。

被权衡过的选项：

| 决策点 | 曾权衡 | 最终选择 | 理由 |
|---|---|---|---|
| "差不多"的判据 | 代码相似 / 能力等价 | 能力等价 | 自主设计必然导致实现不同，只能约束外部行为 |
| 上下文保持 | 依赖长对话 / 外部档案 + 恢复协议 | 外部档案 + 恢复协议 | 上下文无法保证不丢，档案可以重读 |
| 决策形态 | 全部选择题 / 三分 | 封闭、半开放、开放三分 | 选择题会限制设计空间，开放决策也需要中立 |
| 偏离处理 | 拉回基准 / 评审 + 分叉 | 评审后由用户选择 | 设计不同不是错误，能力失守才是 |
| Git 粒度 | 每阶段 / 每小步骤 | 每小步骤 | 与可验证交付对齐，便于回滚与对照 |
| 目标偏移 | 改写主线 / 建分支 | 建分支 | 保留原学习路径，不改写历史 |

**残留风险**：

- 能力基线只能覆盖可黑盒验证的行为；架构质量、可维护性等隐性能力仍需人工判断。
- 黑盒用例可能被学习者"针对测试实现"，需要定期补充边界用例。
- 会话恢复依赖 AI 主动读档案；如果客户端不重新加载 skill，规则仍可能漂移。
- Git 提交把对照档案一并入库；若项目公开，基准的对比信息也会公开，需要用户自行判断。
- 偏离评审可能被触发得过于频繁，增加流程开销；判据需要在实际使用中校准。
- 新增行为用例尚未实跑。

## 关键决策一览

| 决策点 | 曾权衡 | 最终选择 | 主要理由 |
|---|---|---|---|
| 对照策略 | 指定统一技术栈 / 自由选型 | 混合对照：架构层自由、实现层定点 | 兼顾自主选型与可比性 |
| 迭代驱动 | 缺陷驱动 / 增量需求驱动 | 增量需求驱动 | 缺陷驱动会暗示存在标准答案 |
