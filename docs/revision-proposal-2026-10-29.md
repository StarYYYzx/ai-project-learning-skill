## 一、信息隔离与双 AI 模式（决策 1）

### 1.1 定位调整：隔离是增益手段，不是正确性保证

单 AI 模式下，AI 的上下文里持有 `lesson/analysis.md` 的架构决策答案库，要求它决策前"零泄露"依赖模型自律，实际不可靠。v0.6 接受"二元决策泄露"、v0.7 引入答案库，隔离已从"结构保证"退化为"纪律约束"。

**决策**：不再追求单 AI 模式的强隔离，改为**阶段 0 明示风险 + 用户自选**。

改动点：
- `SKILL.md` 阶段 0 第 4 项（运作模式）确认时，附一句话风险声明："单 AI 模式下我持有基准的架构决策答案库，对照前做不到彻底隔离；追求严格隔离请选双 AI 模式。"
- `README.md` 在"两种模式"对比处加同样的声明，并说明各自的适用人群（单 AI：图省事、能接受弱隔离；双 AI：严格自主决策）。

### 1.2 双 AI 模式重新设计：两窗口、两份 skill、不需要 instructor

**核心结论：隔离的单位是窗口（会话），不是角色声明。** 同一窗口内让 AI "扮演"协作助手没有隔离意义——它看得到全部指令与教案。角色由"该窗口安装了什么"决定，不由对话内容指定。

**推荐配置（简化后）**：

| 窗口 | 安装 | 职责 | 能否接触答案 |
|---|---|---|---|
| 窗口 1 | 主 skill（SKILL.md + references/） | 阶段 0/1 产出教案；之后兼任指导老师：发布需求、理解验证、小步骤末对照、里程碑汇总、Git 提交与标签 | 能（其职责即对照答案） |
| 窗口 2 | `roles/project-learning-assistant/SKILL.md` | 陪设计讨论、写代码、写 `notes/step-XX.md` | **不能**（隔离真正需要保护的对象） |

理由：
1. 信息隔离只需要对**实现侧**成立——用户在窗口 2 做设计与决策时不能被答案污染；窗口 1 的指导老师本来就要拿答案做对照，它知道答案无害。
2. 主 skill 在阶段 1 后"切换为指导模式"本来就是它的设计（模式 A 的指导模式职责清单与 instructor 完全一致），instructor 角色在这个配置里是冗余的。
3. 用户操作从"装三份、跑三个窗口"降为"装两份、跑两个窗口"。

**instructor 角色降级为可选**，保留场景：教案已由第三方完成、或用户不想要主 skill 的完整流程、只想请一位"只做对照与评估"的老师。若保留，须按第五节做自包含化。

### 1.3 assistant 窗口的禁读清单（现役漏洞修补）

`roles/project-learning-assistant/SKILL.md` 目前只禁止读取 `notes/step-XX-review.md` 等对照侧文件（其"守则"末条），**未禁止读取 `lesson/`**——而 `lesson/analysis.md` 含架构决策答案库（全文检索确认：assistant 文件中 "lesson" 零命中）。须补充完整禁读清单：

- 禁读：`lesson/`（整个目录）、`notes/step-XX-review.md`、`notes/milestone-XX.md`、`notes/parity.md`
- 允许读：`PROGRESS.md`（限进度部分，见下）、`notes/step-XX.md`（实现侧）、项目代码与测试
- 学生主动要求它看对照内容时，提醒"这属于指导老师窗口"。

**复查时新发现的第二个泄露通道**：assistant 被允许读 `PROGRESS.md`（其"会话恢复"条款），而 `PROGRESS.md` 模板含"决策索引"表，其中"原项目选择"列在里程碑末填入基准选择（`record-template.md:45-48`）。即：即使禁了 lesson/，assistant 仍可从 PROGRESS.md 看到已揭示的基准决策，锚定后续设计讨论。处置二选一：
- 方案 a：决策索引表整体移出 `PROGRESS.md`，并入 `notes/milestone-XX.md`（对照侧文件），PROGRESS.md 只留指向链接；
- 方案 b：保留在 PROGRESS.md，但 assistant 的会话恢复条款改为"只读 PROGRESS.md 的项目信息、里程碑总览与当前步骤表，不读决策索引"。

### 1.4 双 AI 模式操作循环（写入 README）

用户在两窗口间充当消息总线，README 新增"双 AI 模式操作循环"章节，含安装步骤与三个跨窗口转发模板：

**循环五步**：

```
① 窗口1：主 skill 走完阶段 0/1（确认四件事 → 教案 → 建库）
② 窗口1 → 窗口2：复制"需求转发模板"
③ 窗口2：设计讨论 → 用户拍板 → AI 实现 → 写 notes/step-XX.md
④ 窗口2 → 窗口1：复制"完成通知模板"
⑤ 窗口1：理解验证 → 小步骤末对照 → 写 review 档案 → Git 提交 → 发布下一步需求（回到②）
```

**转发模板**（放 README，用户直接复制粘贴）：

- 需求转发：`当前步骤 S<编号>。需求：<粘贴窗口 1 输出的需求、验收标准、决策点>。`
- 完成通知：`S<编号> 已完成，实现摘要与决策理由在 notes/step-XX.md，请对照。`
- （对照后若需返工）返工通知：`对照结论：<$review 要点>。请按以下范围重做：<范围>。`

### 1.5 无 skill 安装能力的客户端降级路径

README 补充：不支持 skill 目录的客户端，把对应 SKILL.md **全文粘贴为该窗口的第一条消息**，效果等价于安装；窗口 2 用 assistant 的文件，窗口 1 用主 skill 文件。

### 1.6 对用户问题的直接回答（记入 README FAQ）

"加载 skill 选好项目后，直接说'你的角色是 xxx'可以吗？"——不可以。同一会话内切换角色等于没有隔离，AI 看得到全部教案。正确做法：隔离靠"两个窗口各装各的 skill"，装了什么就是什么角色，无需口头声明。

## 二、决策中立放宽（决策 2）

### 2.1 取舍记录

v0.4 的机械禁词方案（禁"轻量""工作量大"等一切评价性描述、要求对称枚举）在防引导上有效，但代价是信息量下降、初学者更难决策（dev-history 阶段六已记录此残留风险），且执行上防不住（模型给"可用方案"时天然带倾向）。**结论：放宽为简单中立，允许 AI 给带依据的引导，这对初学者利大于弊。**

### 2.2 新规则（三条，替换原"决策中立"整节）

1. **顺序规则（唯一的硬规则）**：学习者表态（初步倾向 + 理由）之前，AI 不展开利弊分析。用户先产出，AI 再补充——这一条保住生成效应的核心。
2. **AI 可给引导**：给出各选项的事实属性与权衡，可引用用户此前 stated 的约束（如"你担心并发，X 方案的事务正好覆盖"），但须覆盖所有候选、注明"是我的分析，供参考"，不催促、不收窄候选集。
3. **两条底线**：不替用户拍板；拍板后不评价选择对错，按定稿实现。

### 2.3 删除项与保留项

| 处置 | 内容 |
|---|---|
| 删除 | 禁用词表（"推荐/最佳/主流/轻量…"）、"所有选项同一组维度、长度相当"、"决策前零评价"、"被反问时只反推不表态" |
| 保留 | 决策三分（封闭/半开放/开放）、"先请用户讲理由"顺序、半开放决策"用户先提方案、AI 补充"、开放决策"无基准答案"标记、用户跳过设计时提醒一次 |

### 2.4 需同步修改的文件

- `SKILL.md` 执行纪律表"决策前"行改为顺序规则表述
- `references/communication-guide.md` 第 3 节整节重写
- `references/comparison-protocol.md` 第 0/2 节的"中性枚举"措辞同步
- `roles/project-learning-assistant/SKILL.md` "设计讨论"一节同步
- `roles/project-learning-instructor/SKILL.md` 红线中决策中立条目同步
- `references/example-walkthrough.md` 第 2 步示例改为新形态（AI 可以给带依据的分析，但放在学生初步表态之后）
- `evals/behavior-evals.md` 用例 1、用例 4 期望行为改写（失败判定删"出现评价性描述"类，改为"学生表态前 AI 展开利弊"）

### 2.5 风险备注

锚定效应回归：AI 的引导会主观上抬高被引导项。缓冲手段就是顺序规则——学生的初步产出先于 AI 意见存在。此项交给 behavior-evals 实跑观察（见第四节）。

## 三、规则单一事实源化（问题 3）

### 3.1 问题本质

同一条行为规则目前在 3-4 处重复出现（主 SKILL.md 纪律表、communication-guide、两个角色 skill）。修改时漏改任意一处，各客户端加载到不同副本就执行不同规则。历史上已发生 3 次漂移（README"维护约定"自述）；本次评审又发现一处现役漂移：**阶段 0"推荐基准项目不受中立约束"的豁免只写在 communication-guide.md:39，主 SKILL.md 纪律表没有携带**。

### 3.2 方案

**方案 A（推荐）：一处正文，处处引用。**
每条规则的完整表述只存在于一份文件（references/ 或角色文件），其他位置只写一行摘要 + 指针。落地顺序依赖第五节（角色自包含），因为"引用"要求被引用文件在加载范围内。

- 主 SKILL.md 纪律表：保留（它是索引和摘要层，注明"细则见 xxx"）
- communication-guide：作为交流类规则的唯一正文
- 对照类规则正文收敛到 comparison-protocol
- 角色 skill 只保留角色特有内容（分工、档案归属），通用规则用一行摘要 + "完整规则见主包 references/"

**方案 B（最低成本兜底）：保留重复 + 同步清单。**
新增 `docs/sync-checklist.md`，列出"每条规则出现的所有文件与行位"；CHANGELOG 的每次改动条目注明"已同步 N 处"。缺点：靠人工自觉，正是已三次失败的做法。

**建议**：方案 A 为主，方案 B 的 checklist 作为过渡期工具保留。

## 四、evals 实跑与回归纪律（问题 4）

### 4.1 问题本质

`evals/trigger-evals.json`（20 条触发查询，recall ≥ 0.9 / precision ≥ 0.85）与 `evals/behavior-evals.md`（12 个行为用例带失败判定）自 v0.3 建立以来**从未实际执行**，dev-history 三处承认"尚未实跑"（:92、:160、:192），upgrade-log-v0.3.md:79 亦记录"目标是设定值"。这个 skill 的资产全是行为规则，恰是"改 A 处坏了 B 处"的高发区；没有实测，五个版本的规则改动全部处于"应该没问题"状态。

### 4.2 怎么跑（无需写代码也能完成）

- **触发集**：每条 query 单独开一个新会话（装载 skill），发送，记录是否进入阶段 0 / 引用本方法。20 条 ≈ 半小时。
- **行为集**：每个用例单独开会话，按剧本发输入，对照"期望行为 / 失败判定"逐条打勾。12 条 ≈ 1-2 小时（部分用例需要走到对应阶段才能测）。
- 可选脚本化：写批量跑测脚本（逐条开会话、收集回复、人工或 LLM 判分），但**第一轮手工跑足够**，先把基线数据拿到。

### 4.3 立两条纪律（写入 SKILL.md 或 README 维护约定）

1. **发版回归**：改动任何行为规则，必须重跑覆盖该规则的行为用例；结果（日期、通过率、失败用例）记入对应 evals 文件头部。
2. **发版全量**：版本号变更（minor 及以上）时触发集 + 行为集全量跑一遍，CHANGELOG 附实测数字（替代"目标值"）。

### 4.4 用例补充

- 双 AI 隔离 2 条：assistant 不读取 `lesson/` 与对照侧文件（给它含答案的路径让它总结，期望拒绝）；assistant 不执行 `git commit`。
- 术语脚手架 1 条：需求发布中首次出现关键术语，期望附一行"它在本项目里管什么"。
- trigger-evals 标注边界项：query 4、12 属模糊地带（泛学习方法诉求），实跑时单独统计，必要时调 description 措辞。
