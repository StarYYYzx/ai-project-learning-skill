# Skill 升级记录：v0.2 → v0.3

记录一次以"官方规范 + 社区实战经验"为参照的规范化升级：从实际使用反馈出发，调研 skill 编写规范，逐项诊断、修复、验证。适用于理解本轮变更的理由，也作为后续迭代的参照模板。

## 一、升级起因

在真实使用中暴露两个问题：

1. 术语壁垒：AI 在决策提问里使用专业名词，初学者无法判断，卡在决策点。
2. 倾向性推荐：AI 会给"推荐方案"，导致学生按推荐走，自主决策退化为猜测 AI 偏好。

针对问题落地了一套交流规范（v0.2）。但规范落地后产生了新的疑问：整个 skill 的写法本身是否合规？是否还有结构性问题？于是做了一轮以官方规范为基准的对照审查。

## 二、调研依据

| 来源 | 性质 | 采用的关键结论 |
|---|---|---|
| Anthropic 官方《Skill authoring best practices》 | 官方一手 | SKILL.md 控制在 500 行内；引用保持一层深，深层嵌套会导致部分读取；引用需写明触发场景；description 须含"做什么 + 何时用" |
| Agent Skills 开放规范（agentskills.io） | 官方一手 | frontmatter 字段约束：`name` ≤64 字符且与父目录同名；`description` ≤1024 字符；可选 `license`、`metadata`、`compatibility` |
| Anthropic 工程博客《Equipping agents for the real world with Agent Skills》 | 官方一手 | 三层渐进式披露：元数据常驻、SKILL.md 触发时加载、references 按需读取 |
| 跨 6 个客户端的兼容性实测 | 社区实测 | 只用 `name` + `description` 最可移植；斜杠命令、`allowed-tools` 属客户端专属，其他平台会静默忽略 |
| 《删掉 80% 的 Skill，Agent 反而更听话了》实战复盘 | 社区经验 | 红线埋在文档中部时遵循率下降 30-50%；否定指令存在反作用；全局禁令只写一次，重复会互相抢占注意力 |

## 三、问题清单与处置

| 编号 | 问题 | 优先级 | 处置 |
|---|---|---|---|
| 1 | references 引用措辞被动（"按 xxx 拆出""细则见 xxx"），AI 可能不读取引用文件 | P0 | 改为显式读取指令，标注触发场景 |
| 2 | 角色边界口径冲突：指导老师说"不泄露基准细节"，对照协议说"对照阶段可翻阅基准源码" | P0 | 统一为"对照开始前不透露；开始后学生可自行翻阅，AI 不代为展示" |
| 3 | 红线位于文档后 1/3，且全部为否定句 | P0 | 前置为执行纪律表，改为"正向行为 + 附带禁止项" |
| 4 | 主 skill 与两个角色 skill 的规则无同步机制，已漂移过一次 | P0 | README 增加维护约定，明确三处同步要求 |
| 5 | 协作模式说明与红线区重复表述同一规则 | P1 | 合并为纪律表单一来源，前文改为引用 |
| 6 | frontmatter 缺少 license 与元数据 | P1 | 补 `license: MIT`、`metadata.author`、`metadata.version` |
| 7 | 只有格式模板，缺一个跑通全流程的示例 | P1 | 新增 `references/example-walkthrough.md` |
| 8 | 没有任何测试用例 | P2 | 新增 `evals/`（20 条触发查询 + 3 个行为用例） |
| 9 | 斜杠命令在部分客户端无效 | P2 | 命令表补充等价自然语言说法 |
| 10 | README 未反映 v0.2 新增机制 | P2 | 新增"面向初学者的四个机制"章节 |
| 11 | 无版本管理 | P2 | 新增 `CHANGELOG.md` 与版本字段 |

## 四、关键改动前后对比

### 红线组织方式

改动前：文档第 66-73 行一个"红线"章节，7 条否定句。

改动后：文档第 14-28 行的执行纪律表，位于全文前 1/5，形如：

| 场景 | 你要做的 | 不要做 |
|---|---|---|
| 用户实现阶段 | 只列选项、只说各自权衡，把决定权交回用户 | 出现"推荐 / 最佳 / 主流"等倾向词；替用户选技术栈 |
| 对照开始之前 | 只讨论用户自己的方案；必要时解释通用概念 | 透露基准的代码、架构、参数 |

同一规则只出现一次，实现阶段说明改为引用纪律表，消除内部重复。

### 引用方式

改动前：`按 references/decomposition-guide.md 拆出模块结构…`

改动后：`先读取 references/decomposition-guide.md（拆解步骤、产物格式、基准项目筛选标准），据此拆出…`

同时参考文献区从"文件清单"改为"触发场景 → 文件"的映射，符合官方"写明何时读取"的要求。

## 五、验证方式

已完成：

- 结构合规检查：SKILL.md 行数、引用深度、frontmatter 字符合法性、目录命名一致性
- 一致性校验：开源源目录与安装副本逐文件哈希比对
- 冲突审计：检查 references 与角色 skill 之间是否存在互相矛盾的表述（本轮修复 1 处）

待执行（需真实会话）：

- 触发评估：按 `evals/trigger-evals.json` 跑 20 条查询，统计召回率与精确率
- 行为评估：按 `evals/behavior-evals.md` 跑 3 个用例，验证纪律是否被遵守
- 跨模型测试：在 Haiku 级与 Opus 级模型上分别验证（官方建议，指令密度需求不同）

## 六、遗留问题与后续方向

1. 触发评估尚未实跑，description 的召回/精确目标目前只是设定值。
2. 规则在三处刻意重复（角色 skill 需独立安装、无法互相引用），长期存在漂移风险，当前的同步约定靠人工执行，未来可考虑用脚本做一致性检查。
3. 尚未收到第三方使用反馈，缺少外部验证。
4. `name` 采用名词短语而非官方推荐的动名词形式（如 `learning-projects-with-ai`）。因已开源发布、更名有成本，暂不调整。
