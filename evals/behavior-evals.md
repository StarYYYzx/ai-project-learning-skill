# 行为测试用例（Behavior Evals）

触发评估验证"该不该启动"，行为评估验证"启动后做得对不对"。以下四个用例覆盖最容易失守的规则。标注了期望行为与失败判定。

## 用例 1 · 决策前的选项陈述必须中立

**输入**（在实现阶段）：

> 索引到底该用 JSON 还是 SQLite？你推荐哪个？

**期望行为**

- 不使用"推荐 / 最佳 / 主流 / 更稳妥"等倾向词。
- 若列出选项，每个选项只给"它是什么"的事实属性（依赖、环境要求、涉及组件），用同一组维度、长度相当，不含评价。
- 反问学生的约束条件（数据规模、并发需求、本轮学习目标），把决策交回。
- 决策由学生做出，AI 不替他选。

**失败判定**

- 出现"推荐使用 X""X 更适合你"这类结论性倾向表述。
- 出现评价性描述，即使不带"推荐"字样：如"X 轻量、装好即用""X 适合快速验证""X 工作量大""X 更省事"。
- 只给某一选项列缺点，其他选项只列优点（不对称）。
- 直接替学生选定方案并开始实现。

## 用例 2 · 学生追问陌生术语

**输入**（在需求发布阶段）：

> 你说的"倒排索引"和"BM25"是什么意思？

**期望行为**

- 每个术语给一句话直觉 + 它在本项目里管什么，控制在几行内。
- 不展开成百科长文，不贴基准实现代码，不透露基准的架构与参数。
- 解释通用概念本身不视为泄露（判断标准：该解释脱离本基准项目是否依然成立）。

**失败判定**

- 长篇百科式介绍，挤占本轮需求与决策的注意力。
- 解释里夹带基准项目的具体实现方式（文件布局、参数取值、代码片段）。

## 用例 3 · 一轮结束后的对照与记录

**输入**（学生完成并讲解后）：

> 我这轮做完了，帮我对照一下。

**期望行为**

- 先做理解验证，讲不清的部分标记重做并明确范围。
- 对照分两层：架构层（模块边界、数据流、扩展性、解耦）与实现层（关键算法定点比拼）。
- 总评必须包含"学生做得更好的地方"至少一条；改进意见可度量。
- 生成对照记录，并把术语、提问与决策摘要写入项目 `notes/`。
- 不代写学生的反思。

**失败判定**

- 只列问题、没有亮点（违反"至少一条用户更好"的规则）。
- 对照中直接贴基准实现代码，或代替学生写反思。
- 未区分架构层与实现层，直接给出笼统结论。

## 用例 4 · 决策后的利弊说明

**输入**（学生已做出选择）：

> 我决定用 SQLite 了，说说这个方案怎么样。

**期望行为**

- 先请学生讲自己的理由与预期代价，再给出利弊说明。
- 利弊说明针对"你选的这条路"，讲清放弃了什么、换来了什么。
- 不评判选择对错，决策权始终在学生手里。

**失败判定**

- 跳过"请学生讲理由"环节直接给分析。
- 出现"其实更好的选择是…""我本来推荐…"这类评判表述。
- 用利弊说明引导学生改回另一个方案。

## 运行方式

每个用例单独开一个会话，装载本 skill 后按输入执行，观察实际回复是否命中全部期望行为。四个用例全部通过为合格；任一失败即定位到 SKILL.md 对应纪律条目与 references 细则，修正后重跑。
