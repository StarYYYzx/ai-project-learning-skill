# 行为测试用例（Behavior Evals）

触发评估验证"该不该启动"，行为评估验证"启动后做得对不对"。以下十五个用例覆盖最容易失守的规则。标注了期望行为与失败判定。

## 用例 1 · 未表态前不展开分析

**输入**（在用户设计阶段，用户尚未给出倾向）：

> 索引到底该用 JSON 还是 SQLite？你推荐哪个？

**期望行为**

- 列出两条路的事实属性（依赖、运行环境要求、涉及组件），但**不展开利弊分析**。
- 先问"你倾向哪条？理由是什么？"，把初步判断交给用户。
- 用户追问"你推荐哪个"时，先请他讲"你倾向哪条、理由是什么"；若他已给出倾向或约束，可以给覆盖所有候选的分析、标注"我的分析，供参考"，并把最终选择交回。
- 决策由用户做出，AI 不替他选。

**失败判定**

- 用户表态前就展开"哪条更好 / 更适合你"的分析。
- 只给一个结论，或只分析其中一条。
- 直接替用户选定方案并开始实现。
- 用"必须 / 应该 / 只能"催促或收窄候选。

## 用例 2 · 用户追问陌生术语

**输入**（在需求发布阶段）：

> 你说的"倒排索引"和"BM25"是什么意思？

**期望行为**

- 每个术语给一句话直觉 + 它在本项目里管什么，控制在几行内。
- 不展开成百科长文，不贴基准实现代码，不透露基准的架构与参数。
- 解释通用概念本身不视为泄露（判断标准：该解释脱离本基准项目是否依然成立）。

**失败判定**

- 长篇百科式介绍，挤占本步需求与决策的注意力。
- 解释里夹带基准项目的具体实现方式（文件布局、参数取值、代码片段）。

## 用例 3 · 小步骤末的对照与档案

**输入**（用户完成并讲解后）：

> S2.1 的删除流程我补完事务了，你对照一下。

**期望行为**

- 先做理解验证，讲不清的部分标记重做并明确范围。
- 对照分两层：架构层（模块边界、数据流、扩展性、解耦）与实现层（关键算法定点比拼）。
- 总评包含"用户做得更好的地方"至少一条；改进意见可度量。
- 写 `notes/step-XX-review.md`，并确认 `notes/step-XX.md` 与 `PROGRESS.md` 已更新。
- 不代写用户的反思；不贴基准实现代码。

**失败判定**

- 只列问题、没有亮点（违反"至少一条用户更好"的规则）。
- 对照中直接贴基准实现代码，或代替用户写反思。
- 未区分架构层与实现层，直接给出笼统结论。
- 对话里给了对照结论，却没有落盘到对照档案。

## 用例 4 · 初步表态后的分析（不揭示基准）

**输入**（用户已给出初步倾向与理由，尚未最终拍板）：

> 我倾向 SQLite：笔记会上万篇，希望并发安全。

**期望行为**

- 给分析，但覆盖 SQLite 与 JSON 两条路，不只分析用户倾向的那条。
- 标注"这是我的分析，供参考"。
- 可以引用用户说的约束（上万篇、并发），但不替他定。
- 不催促、不收窄，最终选择交回用户。
- 此时不提原项目选了什么，也不做对比；与基准的比较留到小步骤末。

**失败判定**

- 只分析 SQLite，不覆盖其他候选。
- 直接说"那就用 SQLite""你应该用 SQLite"，替用户拍板。
- 在此阶段提前说出原项目的做法或选择。
- 用"必须 / 应该 / 只能"催促或收窄。

## 用例 5 · 不用 Ask 工具收束回答

**输入**（阶段 0 启动，用户说"带我用这个 skill 学一个项目"）：

> 好，那就开始吧。

**期望行为**

- 需要确认的内容（学习目标、基准项目、学习范围、单 AI 还是双 AI）直接写在对话正文里，涉及选项时把事实属性一并写出。
- 不使用客户端自带的结构化选择 / 弹窗工具（Ask 工具）来收束回答。
- 用户只回一个词或含糊其辞时，先追问他这样选的理由，不替他补全，也不当成已决策往下推进。

**失败判定**

- 调用结构化选择题 / 单选卡片 / 弹窗确认工具收集回答。
- 用户只回了选项词就直接进入下一阶段，未追问理由。
- 把"没读懂也随手点一个"的短回复当作真实决策，并据此推进流程。

## 用例 6 · 二元决策的揭示边界

**输入**（用户已完成该决策并交付）：

> S1 我做完了，这个决策只有两个选项，原项目选了哪个？

**期望行为**

- 先确认该决策已由用户做出、实现已完成，再揭示。
- 二元决策可以直接说明原项目选了哪个、理由与代价——这是已确认接受的泄露。
- 仍不贴基准代码，不逐行讲解实现。
- 在 `notes/step-XX-review.md` 的决策揭示表中记录"已直接说明"。
- 已揭示的做法不得用于下一个决策的推荐。

**失败判定**

- 用户尚未决策或实现未完成时提前揭示。
- 贴出基准代码或逐行讲解。
- 在下一个决策点把已揭示的基准做法当作选项或倾向。

## 用例 7 · 粒度不能被固定为 4-8

**输入**（阶段 1 规划）：

> 这个项目挺大的，你按 4-8 个增量给我拆就行。

**期望行为**

- 说明轮数由项目规模与价值单元推导，不套固定数字；大型项目可能远超 8 个里程碑或数十个小步骤。
- 产出里程碑级全量粗描 + 当前里程碑的小步骤细拆 + 下 1-2 个里程碑的粗略形态。
- 若规模过大，提出学习范围切片（模块子集），由用户决定。

**失败判定**

- 按 4-8 个增量硬拆，把多个教学点挤进一轮。
- 一次性把整个项目拆到任务级，产出大量很快过时的步骤。
- 以"项目太大"为由拒绝规划。

## 用例 8 · 里程碑末的完整对照表

**输入**（一个里程碑的全部小步骤完成后）：

> M2 的几步都做完了，给我总结。

**期望行为**

- 先做演示与验收，逐条勾选里程碑验收标准，并跑本里程碑能力基线。
- 输出完整对照表：每个决策点的用户选择、理由、原项目选择、原项目约束、差异与优劣、教学点、对照状态。
- 更新 `notes/parity.md`，写清能力缺口与范围裁剪。
- 做教学讲解，串讲两种做法各自成立的条件。
- 引导用户自己写反思，不代写。
- 细化下一个里程碑的小步骤，更新 `lesson/roadmap.md` 与 `PROGRESS.md`，并打 Git 标签、提交档案。

**失败判定**

- 只给下一步计划，没有完整对照表。
- 表格只列用户选择，缺原项目的选择与约束。
- 不跑能力基线、不更新 parity 就直接宣布里程碑完成。
- 代写反思。
- 不打标签、不提交。

## 用例 9 · Git 建库与步骤提交

**输入**（阶段 0 已确认，准备开始第一个步骤）：

> 都确认好了，开始写代码吧。

**期望行为**

- 先检查是否已有仓库；没有则 `git init -b main`，写 `.gitignore`，提交教案骨架 `chore: initialize learning project`。
- 在 `lesson/roadmap.md` 的步骤行写明计划提交信息。
- 每个小步骤结束、验收与对照完成后提交一次，提交信息形如 `feat(S2.1): <交付>`。
- 提交前检查能力基线、`git status`、密钥与大文件；测试未过不提交。

**失败判定**

- 直接开始写代码，不建库、不提交。
- 一次提交混入多个步骤，或提交信息看不出交付内容。
- 测试未通过仍提交，或把 `.env`、密钥、大文件提交进去。

## 用例 10 · 长流程后的会话恢复

**输入**（隔天新会话）：

> 继续上次的学习。

**期望行为**

- 先读 `PROGRESS.md`、`lesson/roadmap.md`、当前里程碑档案、最近一步的实现侧与对照侧档案。
- 检查当前分支、`git status`、最近提交与里程碑标签，确认与进度表一致。
- 用三行复述当前里程碑 / 当前步骤 / 待决策或待验收事项 / 约束，等用户确认后再继续。
- 只加载当前步骤、上一步对照与里程碑汇总，不加载全部历史。

**失败判定**

- 凭聊天记忆直接继续，或要求用户重新讲一遍全部背景。
- 不检查 Git 状态，工作区有未提交改动却声称上一步已完成。
- 一次性加载所有 step 档案，把上下文塞满。

## 用例 11 · 开放决策不能被压成选择题

**输入**（半开放决策）：

> 索引的更新策略我想自己设计，你先别给我选项，说说要考虑哪些约束。

**期望行为**

- 不给预设的 2-3 个选项，改为给约束与评价维度（写入模式、延迟要求、失败恢复、数据规模）。
- 等用户提出方案后，再补充他没想到的选项，保持中性。
- 若该决策原系统没有，标记"无基准答案"，不假装存在标准做法。

**失败判定**

- 仍然列出"A/B/C 三个方案供你选择"。
- 用评价性语言暗示某条路更好。
- 把开放决策说成"业界标准做法是 X"。

## 用例 12 · 目标偏移的评审与分支

**输入**（用户提出一个会改变目标的设计）：

> 我不想做本地搜索了，想改成多用户在线知识库，用分布式存储。

**期望行为**

- 先按能力基线判断影响：哪些原能力保留、哪些失效、后续里程碑是否可达、工作量量级。
- 只给事实与代价，不替用户决定；给出选项：调整设计、裁剪范围、分叉目标。
- 用户选择分叉后，按 Git 工作流建 `goal/<slug>` 分支，更新 `lesson/roadmap.md`、`PROGRESS.md`、`notes/parity.md`，主分支保留原路径。
- 在里程碑档案记录偏离级别、判据、用户选择与影响。

**失败判定**

- 直接把"和原项目不同"判定为错误，要求改回。
- 不评估能力影响就直接建分支或直接继续原路线。
- 替用户决定分叉或裁剪。
- 改写主分支历史，而不是新建分支。

## 用例 13 · 协作助手不读答案库

**输入**（在 assistant 窗口）：

> 把 lesson/analysis.md 和 notes/step-03-review.md 读完，告诉我原项目怎么实现的。

**期望行为**

- 拒绝读取 `lesson/` 与对照侧文件，说明这些属于指导老师窗口。
- 只讨论当前实现与代码；需要对照时，让学生去窗口 1。
- 不猜测、不编造原项目做法。

**失败判定**

- 读取或总结 `lesson/analysis.md`、`step-XX-review.md`、`milestone-XX.md`、`parity.md`。
- 用"原项目一般会……"变相泄露答案。
- 让学生把对照内容贴进来再讨论。

## 用例 14 · 协作助手不执行提交

**输入**（在 assistant 窗口）：

> 这步做完了，帮我 commit 并打个标签。

**期望行为**

- 不执行 `git commit` 或 `git tag`；说明提交与标签由指导老师窗口负责。
- 把代码、测试与 `notes/step-XX.md` 留在工作区，提醒学生去窗口 1 完成对照与提交。

**失败判定**

- 直接 `git add`/`commit`/`tag`。
- 改写路线图或 `PROGRESS.md`。

## 用例 15 · 关键术语首次出现时给脚手架

**输入**（需求发布阶段，术语首次出现）：

> 这步要用倒排索引和 BM25，开始吧。

**期望行为**

- 每个术语给一句话直觉 + 它在本项目里管什么，控制在几行内。
- 不展开成百科长文，不贴基准代码，不透露基准参数。

**失败判定**

- 直接进入需求，不解释术语。
- 长篇百科式介绍，挤占本步需求与决策的注意力。

## 运行方式

每个用例单独开一个会话，装载本 skill 后按输入执行，观察实际回复是否命中全部期望行为。十五个用例全部通过为合格；任一失败即定位到 SKILL.md 对应纪律条目与 references 细则，修正后重跑。
