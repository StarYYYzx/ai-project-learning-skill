# ai-project-learning

基于 AI 的项目学习法：把任意一个项目变成一次系统学习。装载本 skill 后，指定一个项目，它会自动执行完整的对照式学习闭环。
```
这段是人写的，后面全是ai写的。
总之就是找实习，写简历，肯定需要写个项目啥的。
但这年头真的还有必要手敲代码学项目吗？都什么年代了还在搞古法编程？
于是这个skill就来了
```

```
软件工程分析 → 建 Git 仓库 → 里程碑路线（滚动规划）→ 小步骤迭代（用户设计 → AI 实现 → 理解验证 → 小步骤末对照 → 档案 → 提交）→ 里程碑汇总与 parity → 完成标准评估
```

## 不适用场景

本 skill 不适用于：刷题与考试准备、语法/API 速查、纯概念学习、只需要一次性代码生成的任务。这些场景没有"设计—实现—对照"的闭环，强行使用只会增加仪式负担。

## 为什么这样设计

AI 时代写代码的成本接近零，学习重点从"怎么写"转向"怎么设计、怎么判断"。这套方法建立在两个被反复验证的学习策略上：

- **生成效应**：先自主产出，再看到对照，理解深度远高于先看答案再模仿。
- **对照式反馈**：以成熟实现为基准做差异分析，训练的是评价能力——AI 时代最稀缺的技能。

配套的设计原则：用户设计、AI 实现；先决策后揭示（分级对照）；增量需求驱动（不是缺陷驱动）；基准是参考答案之一（不是标准答案）；理解验证与反思（防止"AI 代写、学生没懂"）。

## 三层粒度

学习路线分三层，数量由项目规模推导，不套固定轮数：

- **项目**：一个有现成代码、可运行的基准。
- **里程碑**：一个可演示的价值单元，结束时做完整对照表与反思。
- **小步骤**：单一可验证交付，内部 1-2 个设计决策，一次会话能完成。

小型工具可能只有 2-3 个里程碑、6-12 个小步骤；大型框架可能是 6-10 个里程碑、40 个以上小步骤，因此用"学习范围切片 + 滚动规划"处理——先粗描全部里程碑，只细拆当前与近期步骤。

## 面向初学者的七个机制

体验中暴露的最大障碍是"术语挡住决策""AI 的倾向性影响学生的自主判断""用选项按钮代替思考""学过的东西散落在对话里"以及"被流程推着走"，为此内置了七条规则：

- **术语脚手架**：关键概念首次出现时附一行解释，说明"它在本项目里管什么"，不展开成百科长文；解释概念不算泄露答案。
- **提问邀请**：每个小步骤开场明示"任何名词随时问"，兜住初学者"不知道自己不知道"的情况。
- **决策中立**：先表态，后分析。学习者给出初步倾向与理由之前，只给事实属性与约束，不展开利弊分析；表态后 AI 可以给覆盖所有候选的分析，标注"我的分析，供参考"，不催促、不收窄、不替学习者拍板。
- **分级揭示**：学习者初步表态前不给基准信息，也不展开分析；表态后只给覆盖所有候选的分析，不涉基准；小步骤末才与原项目对比；二元决策可直接说明原项目选了哪个（接受这部分泄露以换即时教学）；里程碑末汇总完整对照表。
- **对话式提问**：全程不用客户端自带的选择 / 弹窗工具（Ask 工具）收束回答。问题和选项写在对话里，留白等学生用自己的话回复——按钮式回答会让学生"没读懂也随手点一个"，跳过"理解 → 权衡 → 表达"这个学习真正发生的环节。
- **项目档案**：每个小步骤一份实现侧档案；双 AI 另有一份对照侧档案，单 AI 把对照并入同一步档案。另有总进度表、里程碑汇总、术语表、能力基线、评测记录与 parity。提问、决策、对照结论、开发进展都落盘，跨会话可回看。
- **学习者主权**：用户坚持跳过某环节时，提醒一次风险后服从，档案记"跳过"，不反复说教；跳过的理解验证或对照会在 parity 里标"未验证"。

## 工程保障

前面七条解决"怎么教"，下面五条解决"流程长了还靠得住"：

- **能力基线**：每个里程碑从基准抽 5-10 条黑盒用例，与实现无关；里程碑验收必须全过。收尾用 `notes/parity.md` 回答"最后做出来的系统是否和原项目差不多"——判据是能力等价，不是代码相似。
- **Git 工作流**：阶段 1 建库并提交教案；每个小步骤一次提交；每个里程碑打标签；目标偏移建 `goal/<slug>` 分支，主分支保留原路径。
- **会话恢复**：新会话或"继续"时，先读进度表、路线、当前档案并检查 Git 状态，再用三行复述当前状态。档案是唯一事实源，不靠聊天记忆。
- **偏离控制**：设计不同不算偏离；只有能力基线失守、后续里程碑不可达、评测回归或范围爆炸才进入偏离评审。评审只给事实与代价，由学生选择调整设计、裁剪范围或分叉目标。
- **档案负担**：单 AI 把 step 与 review 合并为一份，双 AI 才保留两份；没有设计决策的机械改动走"轻量步骤"模板，只记需求、改动、验证、提交。

## 快速开始

### 模式 A：单 AI（最简单，弱隔离）

1. 把 `SKILL.md` 连同 `references/` 目录装入你的 AI（支持自定义 skill 的客户端）。
2. 说 `/start <项目名>`，或直接描述你想学的项目（如"用这个 skill 带我学 xxx 项目"）。
3. 按 skill 引导走完三阶段：启动确认 → 教案产出（软件工程分析 + 能力基线 + 里程碑路线 + 近期步骤 + Git 建库）→ 小步骤迭代。

实现阶段由 AI 写代码，你负责设计与决策；每个小步骤结束生成学习档案并提交一次，里程碑结束生成完整对照表、更新 parity、打 Git 标签。

**风险声明**：单 AI 模式下，AI 的上下文里持有基准的架构决策答案库，对照前做不到彻底隔离。它靠纪律约束，不靠结构保证。适合图省事、能接受弱隔离的人；追求严格隔离请用模式 B。

### 模式 B：双 AI（两窗口，严格隔离实现侧）

隔离的单位是窗口，不是角色声明。同一窗口内让 AI "扮演"协作助手没有意义——它看得到全部指令与教案。

| 窗口 | 安装 | 职责 | 能否接触答案 |
|---|---|---|---|
| 窗口 1 | 主 skill（`SKILL.md` + `references/`） | 阶段 0/1 产出教案；之后兼任指导老师：发布需求、理解验证、小步骤末对照、里程碑汇总、Git 提交与标签 | 能（对照本来就依赖答案） |
| 窗口 2 | `roles/project-learning-assistant/SKILL.md` | 陪设计讨论、写代码、写 `notes/step-XX.md` | 不能（实现侧必须隔离） |

**操作循环**：

```
① 窗口 1：主 skill 走完阶段 0/1（确认四件事 → 教案 → 建库）
② 窗口 1 → 窗口 2：转发当前步骤的需求、验收标准与决策点
③ 窗口 2：设计讨论 → 学生拍板 → AI 实现 → 写 notes/step-XX.md
④ 窗口 2 → 窗口 1：通知完成，说明实现摘要与决策理由在哪个档案
⑤ 窗口 1：理解验证 → 小步骤末对照 → 写 review → Git 提交 → 发布下一步需求（回到②）
```

**转发模板**（直接复制粘贴）：

- 需求转发：`当前步骤 S<编号>。需求：<粘贴窗口 1 输出的需求、验收标准、决策点>。`
- 完成通知：`S<编号> 已完成，实现摘要与决策理由在 notes/step-XX.md，请对照。`
- 返工通知：`对照结论：<review 要点>。请按以下范围重做：<范围>。`

窗口 2 禁读 `lesson/` 整个目录、`notes/step-XX-review.md`、`notes/milestone-XX.md`、`notes/parity.md`；只读 `PROGRESS.md` 的项目信息、里程碑总览与当前步骤表。`roles/project-learning-instructor/SKILL.md` 是可选角色：教案已由第三方完成、或不想要主 skill 的完整流程时使用。

**不支持 skill 目录的客户端**：把对应 `SKILL.md` 全文粘贴为该窗口的第一条消息，效果等价于安装；窗口 1 用主 skill 文件，窗口 2 用 assistant 文件。

### 使用方法示例

- 想系统学一个开源框架：指定框架仓库为基准项目，目标设为"能独立实现它的核心子集"。
- 想学一门新技术栈：指定一个用该技术栈的成熟项目为基准，按里程碑与小步骤重建。
- 想把学习产出变成真实项目（如个人知识库）：基准选参考实现，数据用你自己的素材。

### 常见问题

**"加载 skill 选好项目后，直接说'你的角色是协作助手'可以吗？"**
不可以。同一会话内切换角色等于没有隔离——AI 看得到全部指令与教案。隔离靠"两个窗口各装各的 skill"，装了什么就是什么角色，不需要口头声明。

**"单 AI 模式能保证不看答案吗？"**
不能。单 AI 的上下文里有答案库，只能靠纪律约束。要结构隔离就用双 AI 两窗口，且窗口 2 不安装主 skill、不读 `lesson/`。

## 命令

斜杠命令在支持自定义命令的客户端可直接使用；其他客户端用自然语言表达同样意图。括号内为等价说法。命令实体文件在 `commands/`，可复制到客户端的命令目录。

| 命令 | 作用 |
|---|---|
| `/start <项目>`（"用这个 skill 带我学 xxx"） | 启动流程 |
| `/resume`（"继续上次的学习"） | 恢复会话，复述当前状态 |
| `/export-roles`（"给我双 AI 模式的角色配置"） | 输出双 AI 模式说明 |
| `/record`（"生成本步学习档案"） | 写当前小步骤的 `notes/step-XX.md` 并更新 `PROGRESS.md` |
| `/commit`（"提交本步"） | 按 Git 工作流提交当前小步骤 |
| `/milestone`（"生成本里程碑对照表"） | 汇总 `notes/milestone-XX.md`、更新 parity、打标签 |
| `/parity`（"更新能力对照报告"） | 更新 `notes/parity.md` |
| `/evaluate`（"跑一次评测"） | 跑能力基线与评测集并记录指标 |
| `/status`（"当前进度如何"） | 当前进度、Git 状态与完成标准达成情况 |

## 安装

把 `SKILL.md`（及 `references/` 目录）放入 AI 客户端的 skills 目录（如 Trae 的 `.trae/skills/`、Claude 的 `~/.claude/skills/`）。双 AI 模式再给窗口 2 安装 `roles/project-learning-assistant/SKILL.md`；`roles/project-learning-instructor/SKILL.md` 是可选角色，需要时再装。

## 维护约定

**单一事实源**：同一类规则只在一处写完整正文，其他位置只写摘要与指针。冲突时以权威文件为准。

| 规则类别 | 权威文件 | 摘要位置 |
|---|---|---|
| 交流、决策、提问、档案 | `references/communication-guide.md` | 主 SKILL 纪律表、assistant skill |
| 对照、分级揭示 | `references/comparison-protocol.md` | 主 SKILL 纪律表、instructor skill |
| 偏离评审、无基准决策 | `references/drift-control.md` | 主 SKILL 纪律表、comparison-protocol |
| Git 建库、提交、标签、分支 | `references/git-workflow.md` | 主 SKILL 纪律表、instructor skill |
| 档案字段与模板 | `references/record-template.md` | 主 SKILL 档案树、instructor skill |
| 能力基线、评测、parity | `references/evaluation-guide.md` | 主 SKILL 阶段 1、instructor skill |
| 里程碑与步骤设计 | `references/increment-design.md` | 主 SKILL 阶段 1 |

角色 skill 需要独立安装，因此保留角色特有的最小执行规则；与主包同装时以主包为准。历史上出现过三次漂移：协作助手曾写着"可以推荐"，与主 skill 的禁止推荐规则直接冲突；示例文档里的选项描述带评价，与当时的中立规则不符；对照时机在指导老师与对照协议之间口径不一致。

**发版回归纪律**：

- 改动任何行为规则，必须重跑覆盖该规则的行为用例；日期、通过率、失败用例记入 `evals/behavior-evals.md` 头部。
- 版本号变更（minor 及以上）时，触发集与行为集全量跑一遍，CHANGELOG 附实测数字，不用"目标值"冒充结果。

版本变化记录在 [CHANGELOG.md](CHANGELOG.md)。
