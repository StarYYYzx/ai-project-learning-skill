# ai-project-learning

基于 AI 的项目学习法：把任意一个项目变成一次系统学习。装载本 skill 后，指定一个项目，它会自动执行完整的对照式学习闭环。
```
这段是人写的，后面全是ai写的。
总之就是找实习，写简历，肯定需要写个项目啥的。
但这年头真的还有必要手敲代码学项目吗？都什么年代了还在搞古法编程？
于是这个skill就来了
```

```
软件工程分析 → 建 Git 仓库 → 里程碑路线（滚动规划）→ 小步骤迭代（用户设计 → AI 实现 → 理解验证 → 小步骤末对照 → 档案 → 提交）→ 里程碑汇总与 parity → 完成标准评估
```

## 为什么这样设计

AI 时代写代码的成本接近零，学习重点从"怎么写"转向"怎么设计、怎么判断"。这套方法建立在两个被反复验证的学习策略上：

- **生成效应**：先自主产出，再看到对照，理解深度远高于先看答案再模仿。
- **对照式反馈**：以成熟实现为基准做差异分析，训练的是评价能力——AI 时代最稀缺的技能。

配套的设计原则：用户设计、AI 实现；先决策后揭示（分级对照）；增量需求驱动（不是缺陷驱动）；基准是参考答案之一（不是标准答案）；理解验证与反思（防止"AI 代写、学生没懂"）。

## 三层粒度

学习路线分三层，数量由项目规模推导，不套固定轮数：

- **项目**：一个有现成代码、可运行的基准。
- **里程碑**：一个可演示的价值单元，结束时做完整对照表与反思。
- **小步骤**：单一可验证交付，内部 1-2 个设计决策，一次会话能完成。

小型工具可能只有 2-3 个里程碑、6-12 个小步骤；大型框架可能是 6-10 个里程碑、40 个以上小步骤，因此用"学习范围切片 + 滚动规划"处理——先粗描全部里程碑，只细拆当前与近期步骤。

## 面向初学者的六个机制

体验中暴露的最大障碍是"术语挡住决策""AI 的倾向性影响学生的自主判断""用选项按钮代替思考"以及"学过的东西散落在对话里"，为此内置了六条规则：

- **术语脚手架**：关键概念首次出现时附一行解释，说明"它在本项目里管什么"，不展开成百科长文；解释概念不算泄露答案。
- **提问邀请**：每个小步骤开场明示"任何名词随时问"，兜住初学者"不知道自己不知道"的情况。
- **决策中立**：决策前只做对称的中性枚举——列出选项与各自的事实属性（依赖、环境要求、涉及组件），不出现任何评价与倾向词；利弊分析放到学生做出决策之后，且先请他讲自己的理由。学生反问"你推荐哪个"时，用提问把他的约束条件反推出来。
- **分级揭示**：决策后只讲所选方案的利弊；小步骤末才与原项目对比；二元决策可直接说明原项目选了哪个（接受这部分泄露以换即时教学）；里程碑末汇总完整对照表。
- **对话式提问**：全程不用客户端自带的选择 / 弹窗工具（Ask 工具）收束回答。问题和选项写在对话里，留白等学生用自己的话回复——按钮式回答会让学生"没读懂也随手点一个"，跳过"理解 → 权衡 → 表达"这个学习真正发生的环节。
- **项目档案**：每个小步骤一份实现侧档案与一份对照侧档案，另有总进度表、里程碑汇总、术语表、能力基线、评测记录与 parity 报告。提问、决策、对照结论、开发进展都落盘，跨会话可回看。

## 工程保障

前面六条解决"怎么教"，下面四条解决"流程长了还靠得住"：

- **能力基线**：每个里程碑从基准抽 5-10 条黑盒用例，与实现无关；里程碑验收必须全过。收尾用 `notes/parity.md` 回答"最后做出来的系统是否和原项目差不多"——判据是能力等价，不是代码相似。
- **Git 工作流**：阶段 1 建库并提交教案；每个小步骤一次提交；每个里程碑打标签；目标偏移建 `goal/<slug>` 分支，主分支保留原路径。
- **会话恢复**：新会话或"继续"时，先读进度表、路线、当前档案并检查 Git 状态，再用三行复述当前状态。档案是唯一事实源，不靠聊天记忆。
- **偏离控制**：设计不同不算偏离；只有能力基线失守、后续里程碑不可达、评测回归或范围爆炸才进入偏离评审。评审只给事实与代价，由学生选择调整设计、裁剪范围或分叉目标。

## 快速开始

### 模式 A：单 AI（最简单）

1. 把 `SKILL.md` 连同 `references/` 目录装入你的 AI（支持自定义 skill 的客户端）。
2. 说 `/start <项目名>`，或直接描述你想学的项目（如"用这个 skill 带我学 xxx 项目"）。
3. 按 skill 引导走完三阶段：启动确认 → 教案产出（软件工程分析 + 能力基线 + 里程碑路线 + 近期步骤 + Git 建库）→ 小步骤迭代。

实现阶段由 AI 写代码，你负责设计与决策；每个小步骤结束生成学习档案并提交一次，里程碑结束生成完整对照表、更新 parity、打 Git 标签。

### 模式 B：双 AI（严格信息隔离）

1. 把 `roles/project-learning-instructor/SKILL.md` 装入 AI-1（指导老师）。
2. 把 `roles/project-learning-assistant/SKILL.md` 装入 AI-2（协作助手）。
3. 用主 skill（或直接指导老师）完成教案产出，然后按步骤：AI-2 陪设计与实现 → AI-1 做小步骤末对照与里程碑汇总。

两个角色严格隔离：协作助手不知道参考答案，保证你先决策、后对照。

### 使用方法示例

- 想系统学一个开源框架：指定框架仓库为基准项目，目标设为"能独立实现它的核心子集"。
- 想学一门新技术栈：指定一个用该技术栈的成熟项目为基准，按里程碑与小步骤重建。
- 想把学习产出变成真实项目（如个人知识库）：基准选参考实现，数据用你自己的素材。

## 命令

斜杠命令在支持自定义命令的客户端可直接使用；其他客户端用自然语言表达同样意图。括号内为等价说法。

| 命令 | 作用 |
|---|---|
| `/start <项目>`（"用这个 skill 带我学 xxx"） | 启动流程 |
| `/resume`（"继续上次的学习"） | 恢复会话，复述当前状态 |
| `/export-roles`（"给我双 AI 模式的角色配置"） | 输出双 AI 模式说明 |
| `/record`（"生成本步学习档案"） | 写当前小步骤的 `notes/step-XX.md` 并更新 `PROGRESS.md` |
| `/commit`（"提交本步"） | 按 Git 工作流提交当前小步骤 |
| `/milestone`（"生成本里程碑对照表"） | 汇总 `notes/milestone-XX.md`、更新 parity、打标签 |
| `/parity`（"更新能力对照报告"） | 更新 `notes/parity.md` |
| `/evaluate`（"跑一次评测"） | 跑能力基线与评测集并记录指标 |
| `/status`（"当前进度如何"） | 当前进度、Git 状态与完成标准达成情况 |

## 安装

把 `SKILL.md`（及 `references/` 目录）放入 AI 客户端的 skills 目录（如 Trae 的 `.trae/skills/`、Claude 的 `~/.claude/skills/`）。角色 skill 同理，分别安装 `roles/` 下的两个。

## 维护约定

规则同时存在于三处：主 `SKILL.md`（及 `references/`）、`roles/project-learning-instructor/SKILL.md`、`roles/project-learning-assistant/SKILL.md`。两个角色 skill 需要独立安装、无法互相引用，因此规则是刻意重复的。

修改任何一条角色行为规则时，必须同步检查这三处，避免出现互相冲突的表述。历史上出现过三次这样的漂移：协作助手曾写着"可以推荐"，与主 skill 的禁止推荐规则直接冲突；示例文档里的选项描述带评价，与决策中立规则不符；对照时机在指导老师与对照协议之间口径不一致。

版本变化记录在 [CHANGELOG.md](CHANGELOG.md)。
