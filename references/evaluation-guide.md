# 评估方案（Evaluation Guide）

"先定评估，再调参数"是工程调优的第一原则：没有量化指标，调优就是玄学。本方法用两层评估回答"最后做出来的系统是否和原项目差不多"：**能力基线**管行为等价，**parity 报告**管最终交代。

## 1. 能力基线（Capability Baseline）

每个里程碑开工前，从基准项目抽取 5-10 条**黑盒用例**。黑盒的意思是只看输入与可观察输出，不看实现：

- 输入：查询、数据、命令或请求
- 期望行为：返回什么、什么时候报错、边界怎么处理
- 来源：基准项目的哪个功能或文档
- 验证方式：命令、脚本或人工检查步骤

写入 `notes/evals.md`。里程碑验收 = 演示脚本通过 + 能力基线全部通过。

能力基线可以给学习者看：它只描述外部行为与边界，不泄露基准的实现、架构或参数。不要附带基准代码、文件布局或内部阈值。

能力基线是"差不多"的第一层定义：**不要求代码相似，要求行为等价**。如果某条能力无法黑盒验证（例如内部架构、扩展性），标注"不可黑盒验证"，改用人工审查并在 parity 报告里写清局限。

## 2. 评测集渐进构建

- 每个小步骤结束时，从**本步新纳入的素材/数据**抽取 3-5 条评测样例。
- 每条样例格式：`id, input, expected_output, expected_source`（`expected_source` 用于验证输出能否溯源，`expected_output` 是理想输出或关键要点）。
- 构建要求：
  - 样例必须能从素材中找到明确出处（考系统能力，不考推理）
  - 每步混入能暴露当前系统短板的样例类型
  - 不重复、覆盖不同素材
- 预期规模：按小步骤数 × 3-5 条累积，不预设固定轮数。

## 3. 指标

- **能力指标**：按项目类型定（检索系统用 Recall@k / MRR；对话系统用回答质量；算法项目用正确率/耗时）。至少一个主指标。
- **溯源指标**（内容型系统）：输出能否追溯到正确来源。
- **回归检查**：每步或每里程碑跑全量能力基线，确认新增功能没有破坏已有能力。

## 4. 评估流程

每个小步骤收尾跑一次，记录到 `notes/evals.md`：

1. 对能力基线与评测集全部执行，记录主指标
2. 抽查 3-5 条输出的质量
3. 对比上一步，解释变化原因（本步新增能力带来的）

## 5. Parity 报告（能力对照）

`notes/parity.md` 在里程碑末更新，收尾时定稿。格式：

```
| 能力 | 原项目表现 | 当前系统 | 证据/指标 | 差异 | 状态 |
|---|---|---|---|---|---|
| 单篇笔记更新后可检索 | 支持 | 支持 | 黑盒用例 B1-B3 通过 | 无 | 具备 |
| 并发写入安全 | 支持 | 支持 | 冒烟脚本 | 实现不同 | 具备 |
| 冷启动 < 全量 30% | 支持 | 未测 | — | 待测 | 部分 |
| 分布式索引 | 不支持 | 不支持 | — | 无 | 不适用 |
```

状态取值：具备 / 部分 / 缺失 / 超出 / 不适用。缺失项必须附"范围裁剪"说明与用户确认记录。

**"差不多"的最终判据**：约定的能力项状态为"具备"或经用户确认的"不适用"，指标达到阶段 1 约定的阈值。不是代码行数、目录结构或技术栈相似。

## 6. 完成标准

阶段 1 与用户约定：评测集规模下限、主指标阈值、溯源指标阈值、能力基线条数。达到即完成学习目标，不要求复现基准全部功能。阈值给建议值并标注可调整。
